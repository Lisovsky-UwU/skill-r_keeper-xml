# XML-интерфейс r_keeper 7

Скилл помогает отвечать на вопросы по XML-интерфейсу r_keeper 7 и составлять рабочие запросы.
Знания взяты из официальных XSD-схем UCS и из проверки команд на живом кассовом сервере
r_keeper 7.26. К конкретному ресторану или стенду скилл не привязан.

## Где что лежит

| Файл | Когда читать |
|---|---|
| `references/protocol.md` | всегда при первом вопросе: транспорт, конверт запроса, статусы ответа, ссылки на объекты (id/code/guid), единицы (тысячные, копейки), кто выполняет команду, блокировки, лицензии, плейсхолдеры в примерах |
| `references/commands.md` | найти команду по задаче: индекс всех команд по группам, с пометкой влияния (R/W/D) |
| `references/commands/<CMD>.md` | конкретная команда: практические замечания, полное дерево запроса и ответа из XSD, проверенные примеры |
| `references/workflows.md` | задача из нескольких шагов: заказ от создания до оплаты, возвраты, предоплата и терминал, доставка, стоп-лист, смены, опрос изменений |
| `references/refnames.md` | какой справочник стоит за элементом (Table -> TABLES, OrderCategory -> UNCHANGEABLEORDERTYPES...) и как его читать |
| `schemas/*.xsd` | первоисточник - когда в сводке чего-то не хватает. Схемы принадлежат UCS и могут отсутствовать (тогда в папке только README); справочник `references/` от них не зависит |
| `scripts/rk7.py` | отправить запрос на стенд (см. ниже) |
| `scripts/xsd_to_reference.py` | перегенерировать `references/commands/` из новой версии XSD |

Файлы команд крупные, поэтому ищи по ним точечно (grep по имени атрибута или тексту ошибки), а не
читай все подряд.

## Как отвечать на вопрос

1. Определи команду или команды. Если пользователь описал задачу словами - найди ее в
   `commands.md` или `workflows.md`; если вставил XML или ошибку - начни с `commands/<CMD>.md`.
2. Прочитай раздел "Практика" в файле команды: там то, что сервер делает не так, как написано в XSD.
   Это частая причина ошибок, поэтому не пропускай его.
3. Дай готовый к отправке XML целиком, а не фрагмент: `<?xml ...?>`, `<RK7Query>`, `<RK7CMD CMD="...">`.
   Значения, которых ты не знаешь, оставь плейсхолдерами `{{имя}}` и скажи, откуда их взять
   (таблица в protocol.md, раздел 9) - выдуманный id выглядит правдоподобно, но не сработает.
4. Явно напомни про единицы, если в запросе есть количества или суммы: quantity в тысячных,
   деньги в копейках. Это самая частая ошибка интеграторов.
5. Если команда меняет данные, скажи, что она делает необратимого (закрывает заказ, печатает
   фискальный чек, удаляет чек), и какие идентификаторы из ответа понадобятся дальше.
6. Различай, что известно из схемы, что проверено на сервере (примеры и "Практика"), а что -
   твое предположение. Схемы - срез определенной версии, сервер может вести себя иначе.

При разборе ошибки смотри на `Status`: `Query Parse Error` - сломан сам XML;
`Bad Query Parameters` - неверный атрибут или `Unknown command` (команда не для этого узла, см.
protocol.md, раздел 6); `Query Executing Error` - бизнес-ошибка, ее текст обычно прямо называет
причину (нет права, не та причина удаления, заказ заблокирован).

## Проверка на живом стенде

Проверяй запрос на стенде, только если пользователь дал к нему доступ. Адрес, логин и пароль бери
у пользователя и передавай через переменные окружения на время сессии; не записывай их в файлы
скилла и в ответы.

```bash
export RK7_HOST=host:port RK7_USER=... RK7_PASSWORD=... RK7_INSECURE=1   # Windows: set / $env:
python scripts/rk7.py --cmd GetSystemInfo --summary          # проверить связь
python scripts/rk7.py query.xml --var orderGuid={...}        # отправить запрос из файла
python scripts/rk7.py --fragment '<RK7CMD CMD="GetOrder"><Order guid="{...}"/></RK7CMD>'
```

Скрипт печатает строку `HTTP | Status | RK7ErrorN | ErrorText` в stderr и тело ответа в stdout.
Код выхода: 0 - Ok или No changes, 1 - ошибка сервера, 2 - нет связи. `RK7_INSECURE=1` нужен почти
всегда: у r_keeper самоподписанные сертификаты со слабыми ключами.

Как вести себя на стенде:
- Начни со справочников: получи реальные id станции, работника, стола, блюда, валюты через
  `GetRefData` / `GetOrderMenu`, а не подставляй значения из примеров.
- Команды с влиянием **R** запускай свободно. **W** (создают и меняют заказы, печатают) - можно на
  тестовом стенде, но создавай для этого свои заказы и не трогай чужие. **D** (закрытие смен,
  удаление чеков, ClearDishRests, SetRefData, ReloadWorkUdb, DeliverySetOrderNumGen) - только после
  явного согласия пользователя, даже на тестовом стенде: они затрагивают весь ресторан.
- Не запускай без нужды OpenWebForm и DeliveryEditOrder: они открывают окно на кассе, не отвечают до
  его закрытия, а DeliveryEditOrder оставляет заказ заблокированным, пока его не отпустят на кассе.
- `Status="Ok"` не доказывает, что разметка верна: сервер молча игнорирует незнакомые элементы.
  Проверяй результат следующим запросом (например, `GetOrder` после `SaveOrder`).
- Убирай за собой: удаляй созданные тестовые заказы (VoidOrder / DeliveryVoidOrder), закрывай
  визиты. Учти, что упавший DeliveryPostOrder может оставить пустой заказ доставки.
- В ответе пользователю приводи фактический Status и ErrorText - это ценнее пересказа.

## Новая версия XSD

Если у пользователя есть свежий набор схем, положи его в `schemas/` (структура - в `schemas/README.md`) и выполни
`python scripts/xsd_to_reference.py schemas .` из папки скилла. Скрипт перепишет
`references/commands/` и `commands.md`, а ручные заметки и примеры возьмет из
`references/command_notes.json` - новые наблюдения записывай туда же, чтобы они пережили перегенерацию.
